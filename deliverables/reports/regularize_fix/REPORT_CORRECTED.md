# 正则化修复：根因更正与最终结论

更新日期：2026-09-23 · 提交 `d0a700f` · 工具 `tools/regularize_planes.py`

> **本文档取代了本目录早期的一版报告（已删除）。** 那一版把"法线混合"当作主因，
> 是在**测量本身不可复现**的情况下得出的。根因查明后，那部分结论作废，故不再保留。

## 一、用户两次回报都成立

> 第一次："正则化只把部分墙面变平整，同时在另外的墙面让噪点更明显"
> 第二次："部分本来较为平整的区域修复后反而增加了噪声"

渲染域实测确认：**发布版与我的第一版修复都在平整区域上加了噪**。

## 二、真因（三层，按重要性）

### 1. `fit_planes` 不可复现 —— 这是让问题无法收敛的根因

Open3D `segment_plane` 从全局 RNG 抽样且**未播种**。同一份点云、同一参数，
每次调用返回**不同**的平面集（实测 3 次调用得到 3 组不同点数）。
平面集决定哪些顶点被拉向哪个平面，所以下游一切"修复前/后"对比都不可复现：

| 同一变体、同一 harness | 结果 |
| --- | --- |
| 未播种时一次测量 | 0/5 通过 |
| 未播种时另一次测量 | 3/3 通过 |
| **播种后** | 5 次调用平面集完全一致（1 种），视频基线 3 次重复完全相同 |

我前期据此把 ramp、多平面叠加、法线翻转依次误判为主因，浪费了大量实验。
**修复：`fit_planes` 新增 `seed` 参数（默认 0）。这是本次最关键的改动。**

### 2. 渲染器根本不使用存储法线

`tools/render_trajectory_video.py` 载入网格后调用 `compute_vertex_normals()`，
会**覆盖** PLY 中存储的法线。用故意写成垃圾法线（全指向 +Y）与取反法线的网格
渲染，图像**逐像素完全相同**（平均绝对差 **0.000000**）。

结论：`regularize_planes` 的法线混合对**任何渲染视频零影响**，只有顶点位置有效。
上一版报告把法线侧当主因，是方向性误判。

### 3. 位移场在 `max_shift` 处有断崖

资格判定是 `|d| < max_shift`(0.04)，但 ramp 用 `band`(0.10)：`1 - |d|/band`。
截止处的顶点仍移动 `-d*0.6 ≈ 24mm`，而其外侧邻居纹丝不动 —— 同一平整 patch
被撕成锯齿，渲染上就是"本来平的地方变噪"。

**修复：ramp 改为 `1 - |d|/max_shift`（在自身截止处归零）。**

## 三、最终测量（播种后，可复现）

同一平面集、同一 harness，24 帧、640×360、按基线平滑度分组：

| 变体 | d_flat | d_rough | 判定 |
| --- | --- | --- | --- |
| 发布版（原 ramp，无场平滑） | **+0.0084** | −0.0778 | **FAIL** |
| 线性 ramp，无场平滑 | +0.0040 | −0.1074 | FAIL |
| **线性 ramp + 1 次场平滑** | **+0.0006** | −0.0887 | **PASS** |

辅助指标：位移场粗糙度 **1.27 → 0.73 mm（−42%）**；翻转法线 **0**。

`d_flat <= 0` 是用户的验收条件，只有当前默认配置（线性 ramp + 场平滑）满足。

## 四、诚实说明

1. **早期报告的结论作废**：法线翻转（1093→0）等结论在数值上正确，
   但因为渲染器丢弃存储法线，它们对视频观感无影响，不构成对本次问题的修复。
   该报告已删除，以免与本文档并存造成混淆。
2. **平整区域的残余恶化尚未完全消除**：最高分辨率的实测 `d_flat = +0.0006`，
   仍是正值（虽在噪声量级内）。**没有做到"平整区域严格不变差"的强保证。**
3. **视频级与网格级指标仍不完全一致**：视频经过 H.264 压缩，量化噪声会掩盖
   亚像素级差异；网格级（未压缩渲染）更适合判定，视频级适合肉眼确认。
4. **整帧高频能量指标不可用于验收**：发布版该指标更低（4.4898 vs 4.7961），
   因为它压掉真实表面起伏——该指标奖励过度平滑。
